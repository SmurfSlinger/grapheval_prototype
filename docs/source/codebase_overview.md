# Codebase overview

GraphEval is organized around a Python pipeline that turns trusted context into
graph facts, extracts claims from an LLM answer, evaluates those claims, and
optionally sends structured feedback back to the model for another iteration.

## Main execution path

The primary research execution starts in:

`src.pipeline.decomposed_backtracking_runner.DecomposedBacktrackingRunner`

A benchmark run is normally started by:

`scripts/run_multihop_benchmark.py`

At a high level, one execution follows this path:

1. `DecomposedBacktrackingRunner` creates an execution scope and prepares the question.
2. `QuestionSplitter` may divide a compound question into sub-questions.
3. `ContextTripleExtractor` converts trusted context into FACT triples.
4. `AnswerGenerator` produces the initial answer.
5. Each sub-question is handled by `KgcIterationEngine`.
6. Answer text is converted into CLAIM triples.
7. Claims are validated and aligned to the trusted graph schema.
8. `GraphComparator` labels claims as supported, contradicted, or lacking evidence.
9. Question-target and trusted-evidence-path checks determine whether the answer is resolved.
10. If needed, structured feedback is built and `BacktrackingReviser` asks the LLM to revise.
11. Neo4j stores execution-scoped FACT and CLAIM relationships.
12. Sub-question results are combined and returned to the benchmark or API caller.

## Main packages

### `src.models`

Shared dataclasses, enums, result objects, FACT/CLAIM representations, iteration
records, and stop reasons.

### `src.llm`

LLM provider interface and implementations, including the Ollama provider used
for local model execution.

### `src.pipeline`

The main GraphEval implementation. Important modules include:

- `decomposed_backtracking_runner` — top-level orchestration
- `kgc_iteration` — bounded per-sub-question evaluation/revision loop
- `context_triple_extractor` — trusted FACT extraction
- `triple_extractor` — CLAIM extraction from model answers
- `structured_triple_validation` — structured-output validation
- `kgc_schema_aligner` — deterministic claim/schema alignment
- `graph_comparator` — FACT/CLAIM comparison and labels
- `question_target` — identifies and evaluates the requested answer target
- `evidence_path_resolver` — validates trusted FACT paths
- `backtracking_feedback_builder` — constructs revision feedback
- `backtracking_reviser` — performs LLM revision
- `working_kgc` — in-memory trusted graph state
- `sub_answer_combiner` — combines sub-question results

### `src.storage`

Neo4j persistence. `neo4j_store.py` stores and reads execution-scoped FACT and
CLAIM relationships. Evaluation and stop decisions remain in Python.

### `src.evaluation`

Experiment-level metrics and evaluation helpers.

### `src.benchmarks`

Benchmark definitions and benchmark catalog support.

### `api`

FastAPI interface used by the local demonstration frontend.

## Research and benchmark entry points

The official multihop experiment is run through:

`scripts/run_multihop_benchmark.py`

Experiment analysis is performed by scripts under `scripts/`, while preserved
results are under `results/research/`.

The detailed pages under **Python code reference** are generated by Sphinx
directly from the modules in `src/` and `api/`.
